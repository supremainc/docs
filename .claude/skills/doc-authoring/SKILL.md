# 문서 공동 작성 워크플로우 (한국어)

이 스킬은 사용자와 함께 문서를 협업하여 작성하기 위한 구조화된 워크플로우를 제공합니다. Claude는 능동적인 가이드 역할을 하며, 사용자를 다음 세 단계로 안내합니다: **컨텍스트 수집 → 구조화 및 다듬기 → 독자 테스트**.

기술 문서(매뉴얼, API 레퍼런스, 릴리스 노트, 보안 가이드 등), 제안서, 스펙 문서, 의사결정 문서 등 구조화된 글쓰기가 필요한 모든 작업에 적용할 수 있습니다.

## 이 워크플로우를 제안할 시점

**트리거 조건:**
- 사용자가 문서 작성을 언급: "문서 써야 해", "매뉴얼 작성해줘", "가이드 초안 잡아줘", "제안서 써줘"
- 특정 문서 유형을 언급: 기술 스펙, 의사결정 문서(decision doc), 기획서, RFC, 보안 가이드
- 본격적인 글쓰기 작업을 시작하려는 낌새가 보일 때

**제안 방식:**
사용자에게 문서 공동 작성을 위한 구조화된 워크플로우를 제안합니다. 3단계를 설명하세요:

1. **컨텍스트 수집**: 사용자가 관련 정보를 모두 제공하고, Claude가 명확화 질문을 던짐
2. **구조화 및 다듬기**: 섹션별로 브레인스토밍과 편집을 반복하며 문서를 완성
3. **독자 테스트**: 아무 배경 지식이 없는 새 Claude로 문서를 테스트해 독자 입장에서 막히는 부분을 미리 잡아냄

이 방식이 문서가 다른 사람(그리고 그 사람이 Claude에 붙여넣었을 때도)에게 잘 통하도록 돕는다는 점을 설명하세요. 이 워크플로우를 시도할지, 자유롭게 작성할지 물어보세요.

사용자가 거절하면 자유 형식으로 작업합니다. 수락하면 1단계로 진행합니다.

## 1단계: 컨텍스트 수집

**목표:** 사용자가 아는 것과 Claude가 아는 것 사이의 간극을 좁혀서, 이후 단계에서 정확한 가이드를 제공할 수 있도록 합니다.

### 초기 질문

문서에 대한 메타 정보를 먼저 물어보세요:

1. 어떤 종류의 문서인가요? (예: 기술 스펙, 사용자 매뉴얼, API 레퍼런스, 의사결정 문서, 제안서). Suprema 문서 사이트에 게재할 문서라면 Tutorial(기초 개념 학습) / How-to guide(특정 작업 수행) / Reference guide(상세 정보 참조) 중 어디에 해당하는지도 함께 확인하세요 — 유형에 따라 이후 섹션 구조가 달라집니다.
2. 주요 독자는 누구인가요? (예: 개발자, 파트너사 엔지니어, 최종 사용자, 내부 팀)
3. 이 문서를 읽고 나서 독자가 어떤 행동/이해에 도달하길 원하나요?
4. 따라야 할 템플릿이나 정해진 형식이 있나요? (예: Docusaurus 문서 구조, 사내 문서 양식)
5. 그 외에 알아둬야 할 제약사항이나 맥락이 있나요? (예: 다국어 번역 예정 여부, 대상 언어)

짧게 요약해서 답해도 되고, 편한 방식으로 정보를 던져도 된다고 안내하세요.

**사용자가 템플릿이나 문서 유형을 언급한 경우:**
- 참고할 템플릿 문서가 있는지 확인
- 공유 문서 링크를 제공하면 적절한 연동 도구로 가져오기
- 파일을 제공하면 읽기

**기존 공유 문서를 수정하는 경우:**
- 적절한 연동 도구로 현재 상태 읽기
- 이미지에 대체 텍스트(alt-text)가 있는지 확인
- 대체 텍스트가 없는 이미지가 있다면, 다른 사람이 Claude로 이 문서를 이해하려 할 때 이미지를 볼 수 없다는 점을 설명하고 대체 텍스트 생성 여부를 물어보세요. 원한다면 각 이미지를 채팅에 붙여넣어 달라고 요청하세요.

### 정보 덤핑

초기 질문에 답변을 받은 후, 사용자가 가진 모든 맥락 정보를 쏟아내도록 유도하세요. 다음과 같은 정보를 요청합니다:
- 프로젝트/문제의 배경
- 관련된 팀 내 논의나 공유 문서 (예: Jira 티켓, Slack 스레드, 기획 문서)
- 왜 다른 대안을 채택하지 않았는지
- 조직 맥락 (팀 역학, 과거 이슈, 관련 부서 간 조율 사항)
- 일정 압박이나 제약사항
- 기술 아키텍처나 의존성 (예: 관련 API 스펙, SDK 버전, 연동 시스템)
- 이해관계자들의 우려사항

정리하지 말고 그냥 다 꺼내놓으라고 안내하세요. 여러 방식으로 맥락을 제공할 수 있다고 알려주세요:
- 생각나는 대로 정보 덤핑
- 참고할 팀 채널이나 스레드 안내
- 공유 문서 링크 제공

**연동 도구(Slack, Google Drive, SharePoint, 기타 MCP 서버 등)를 사용할 수 있는 경우:** 이를 활용해 맥락을 직접 가져올 수 있음을 안내하세요.

**연동 도구가 없고 claude.ai/Claude 앱을 사용 중인 경우:** Claude 설정에서 커넥터를 활성화하면 메시징 앱이나 문서 저장소에서 직접 맥락을 가져올 수 있다고 제안하세요.

초기 덤핑이 끝나면 명확화 질문을 던질 것이라고 안내하세요.

**컨텍스트 수집 중:**

- 사용자가 팀 채널이나 공유 문서를 언급하면:
  - 연동 도구가 있다면: 지금 바로 읽어보겠다고 안내한 뒤 해당 도구 사용
  - 연동 도구가 없다면: 접근할 수 없음을 설명하고, 설정에서 커넥터를 활성화하거나 관련 내용을 직접 붙여넣어 달라고 요청

- 사용자가 잘 모르는 엔티티/프로젝트를 언급하면:
  - 연결된 도구로 검색해볼지 물어보고, 사용자 확인을 받은 후 검색

- 사용자가 맥락을 제공하는 동안, 파악된 내용과 아직 불분명한 부분을 계속 추적

**명확화 질문하기:**

사용자가 초기 덤핑을 마쳤다고 신호를 보내면(또는 충분한 맥락이 제공된 후), 이해를 확실히 하기 위한 명확화 질문을 던지세요.

맥락의 공백을 바탕으로 5~10개의 번호가 매겨진 질문을 생성합니다.

축약형으로 답변해도 된다고 안내하세요 (예: "1: 네, 2: #채널 참고, 3: 아니요, 하위 호환성 때문에"), 문서 링크를 걸거나, 채널을 알려주거나, 그냥 계속 정보를 덤핑해도 됩니다. 사용자에게 가장 편한 방식이면 됩니다.

**종료 조건:**
질문들이 기본적인 설명 없이도 엣지 케이스나 트레이드오프를 물어볼 수 있는 수준의 이해를 보여줄 때, 충분한 맥락이 모인 것으로 간주합니다.

**전환:**
이 단계에서 더 추가할 맥락이 있는지, 아니면 문서 작성으로 넘어갈지 물어보세요.

사용자가 더 추가하길 원하면 그렇게 하고, 준비되면 2단계로 진행합니다.

## 2단계: 구조화 및 다듬기

**목표:** 브레인스토밍, 선별, 반복적 정교화를 통해 섹션별로 문서를 구축합니다.

**사용자에게 설명할 내용:**
문서가 섹션별로 만들어질 것이라고 설명하세요. 각 섹션마다:
1. 무엇을 포함할지 명확화 질문
2. 5~20개 옵션 브레인스토밍
3. 사용자가 유지/제거/결합할 항목 선택
4. 해당 섹션 초안 작성
5. 정교한 수정을 통한 다듬기

가장 불확실한 부분이 많은 섹션부터 시작하고, 나머지를 진행하세요 (기술 스펙이면 보통 기술적 접근 방식, 의사결정 문서면 핵심 제안 부분).

**섹션 순서 정하기:**

문서 구조가 명확하다면:
어느 섹션부터 시작할지 물어보세요.

불확실한 부분이 가장 많은 섹션부터 시작하도록 제안하세요. 의사결정 문서라면 보통 핵심 제안 부분, 스펙 문서라면 보통 기술적 접근 방식입니다. 요약 섹션은 마지막에 작성하는 것이 좋습니다.

**How-to guide인 경우:** 상황/목적(Why) → 실행 방법(How) → 상세 정보(What) 3단 구조를 기본 섹션 뼈대로 제안하세요. 사용자 중심 설계, 인지 부하 최소화, 스캔 가능성을 기준으로 섹션 순서를 정합니다.

사용자가 어떤 섹션이 필요한지 모른다면:
문서 유형과 템플릿을 바탕으로 3~5개의 적절한 섹션을 제안하세요.

이 구조가 괜찮은지, 조정하고 싶은지 물어보세요.

**구조 확정 후:**

모든 섹션에 대해 자리표시자(placeholder) 텍스트가 있는 초기 문서 구조를 만듭니다.

**Artifacts를 사용할 수 있는 경우:**
`create_file`을 사용해 아티팩트를 만듭니다. Claude와 사용자 모두 작업할 뼈대를 갖게 됩니다.

모든 섹션의 초기 구조와 자리표시자가 생성될 것이라고 안내하세요.

모든 섹션 제목과 "[작성 예정]" 같은 간단한 자리표시자 텍스트로 아티팩트를 만드세요.

스캐폴드 링크를 제공하고 각 섹션을 채워나갈 시점임을 알리세요.

**Artifacts를 사용할 수 없는 경우:**
작업 디렉토리에 마크다운 파일을 만듭니다. 적절한 이름을 붙이세요 (예: `의사결정문서.md`, `기술스펙.md`).

초기 구조와 자리표시자가 생성될 것이라고 안내하세요.

모든 섹션 제목과 자리표시자로 파일을 만드세요.

파일명이 생성되었음을 확인하고 각 섹션을 채워나갈 시점임을 알리세요.

**각 섹션마다 다음을 반복:**

### 1단계: 명확화 질문

[섹션명] 섹션 작업을 시작한다고 알리세요. 무엇을 포함해야 할지 5~10개의 명확화 질문을 던지세요:

맥락과 섹션의 목적을 바탕으로 5~10개의 구체적인 질문을 생성합니다.

축약형으로 답변하거나 중요한 부분만 짚어줘도 된다고 안내하세요.

### 2단계: 브레인스토밍

[섹션명] 섹션을 위해 포함될 수 있는 항목을 5~20개(섹션 복잡도에 따라) 브레인스토밍합니다. 다음을 살펴보세요:
- 사용자가 언급했지만 잊혀진 맥락
- 아직 언급되지 않은 관점이나 고려사항

섹션 복잡도에 따라 5~20개의 번호가 매겨진 옵션을 생성합니다. 마지막에는 더 많은 옵션을 원하는지 물어보세요.

### 3단계: 선별

어떤 항목을 유지/제거/결합할지 물어보세요. 다음 섹션에서 우선순위를 파악하는 데 도움이 되도록 간단한 이유도 함께 요청하세요.

예시 제공:
- "1, 4, 7, 9 유지"
- "3 제거 (1과 중복)"
- "6 제거 (독자가 이미 알고 있는 내용)"
- "11과 12 결합"

**사용자가 자유 형식으로 피드백을 주는 경우** (예: "괜찮은 것 같아" 또는 "대부분 좋은데...") 번호 선택이 아니어도, 사용자의 의도를 파악해 진행하세요. 유지/제거/변경하고 싶은 부분을 파악해 적용하세요.

### 4단계: 공백 확인

선택한 내용을 바탕으로, [섹션명] 섹션에 빠진 중요한 내용이 있는지 물어보세요.

### 5단계: 초안 작성

`str_replace`를 사용해 이 섹션의 자리표시자 텍스트를 실제 초안 내용으로 교체합니다.

선택된 내용을 바탕으로 지금 [섹션명] 섹션 초안을 작성한다고 알리세요.

**Artifacts를 사용하는 경우:**
초안 작성 후 아티팩트 링크를 제공합니다.

읽어보고 바꿀 부분을 알려달라고 요청하세요. 구체적으로 짚어줄수록 다음 섹션 작업에 도움이 된다는 점을 알려주세요.

**파일을 사용하는 경우 (아티팩트 없음):**
초안 작성 후 완료를 확인합니다.

[섹션명] 섹션이 [파일명]에 작성되었다고 안내하세요. 읽어보고 바꿀 부분을 알려달라고 요청하세요.

**첫 섹션 작성 시 사용자에게 안내할 핵심 사항:**
문서를 직접 수정하는 대신, 무엇을 바꿔야 하는지 알려달라고 요청하세요. 이렇게 하면 다음 섹션에서 사용자의 스타일을 더 잘 파악할 수 있습니다. 예: "X 항목 삭제 - 이미 Y에서 다뤘음", "세 번째 문단을 더 간결하게".

### 6단계: 반복적 정교화

사용자가 피드백을 줄 때마다:
- `str_replace`로 수정 적용 (문서 전체를 다시 출력하지 않음)
- **Artifacts를 사용하는 경우:** 수정마다 아티팩트 링크 제공
- **파일을 사용하는 경우:** 수정 완료만 확인
- 사용자가 문서를 직접 수정하고 읽어달라고 하면: 변경 사항을 파악해 두고 다음 섹션 작업 시 참고 (사용자의 선호를 보여주는 신호)

사용자가 해당 섹션에 만족할 때까지 **반복**합니다.

전반적인 일관성, 흐름, 완성도를 검토하세요.

독자 테스트로 넘어갈지, 다른 부분을 더 다듬을지 물어보세요.

## 3단계: 독자 테스트

**목표:** 배경 지식이 없는 새 Claude로 문서를 테스트해서, 실제 독자에게 잘 통하는지 검증합니다.

**사용자에게 설명할 내용:**
이제 문서가 실제로 독자에게 잘 통하는지 테스트할 것이라고 설명하세요. 작성자에게는 당연하지만 다른 사람에게는 혼란스러울 수 있는 사각지대를 잡아냅니다.

### 테스트 방식

**서브에이전트를 사용할 수 있는 경우 (예: Claude Code):**

사용자 개입 없이 직접 테스트를 수행합니다.

#### 1단계: 독자 질문 예측

독자가 이 문서를 발견하고 읽으려 할 때 던질 만한 질문을 예측할 의사를 알리세요.

독자가 실제로 물어볼 만한 5~10개의 질문을 생성합니다.

#### 2단계: 서브에이전트로 테스트

이 질문들을 이 대화의 맥락이 전혀 없는 새 Claude 인스턴스로 테스트할 것이라고 안내하세요.

각 질문에 대해, 문서 내용과 질문만 가지고 서브에이전트를 호출합니다.

각 질문에 대해 "독자 Claude"가 맞게 답한 부분과 틀린 부분을 정리합니다.

#### 3단계: 추가 점검 수행

추가 점검을 수행할 것이라고 알리세요.

모호함, 잘못된 가정, 모순을 확인하도록 서브에이전트를 호출합니다.

발견된 문제를 정리합니다.

#### 4단계: 보고 및 수정

문제가 발견되면:
"독자 Claude"가 어려움을 겪은 부분을 보고하세요.

구체적인 문제를 나열하세요.

이 공백을 수정할 의사를 밝히세요.

문제가 있는 섹션에 대해 2단계(구조화 및 다듬기)로 돌아갑니다.

---

**서브에이전트를 사용할 수 없는 경우 (예: claude.ai 웹 인터페이스):**

사용자가 직접 테스트를 수행해야 합니다.

#### 1단계: 독자 질문 예측

사람들이 이 문서를 발견하고 읽으려 할 때 어떤 질문을 할지 물어보세요. Claude.ai에 뭐라고 입력할까요?

독자가 실제로 물어볼 만한 5~10개의 질문을 생성합니다.

#### 2단계: 테스트 설정

테스트 방법을 안내하세요:
1. 새 Claude 대화 열기: https://claude.ai
2. 문서 내용을 붙여넣거나 공유 (공유 문서 플랫폼에 커넥터가 활성화되어 있다면 링크 제공)
3. 생성된 질문들을 "독자 Claude"에게 던지기

각 질문에 대해 "독자 Claude"가 다음을 제공하도록 지시하세요:
- 답변
- 모호하거나 불분명했던 부분
- 문서가 이미 알고 있다고 가정하는 지식/맥락

"독자 Claude"가 정확한 답을 주는지, 오해하는 부분이 있는지 확인하세요.

#### 3단계: 추가 점검

"독자 Claude"에게 다음도 물어보세요:
- "이 문서에서 독자에게 모호하거나 불분명할 수 있는 부분은 어디인가요?"
- "이 문서는 독자가 이미 알고 있다고 가정하는 지식이나 맥락이 무엇인가요?"
- "내부적으로 모순되거나 일관성 없는 부분이 있나요?"

#### 4단계: 결과 기반 반복

"독자 Claude"가 틀렸거나 어려워한 부분을 물어보세요. 그 공백을 수정할 의사를 밝히세요.

문제가 있는 섹션에 대해 구조화 및 다듬기 단계로 돌아갑니다.

## 효과적인 가이드를 위한 팁

**어투:**
- 직접적이고 절차적으로 안내하기
- 사용자 행동에 영향을 줄 때만 짧게 이유를 설명하기
- 이 방식을 "판매"하려 하지 말고, 그냥 실행하기

**이탈 상황 처리:**
- 사용자가 특정 단계를 건너뛰고 싶어하면: 건너뛰고 자유롭게 작성할지 물어보기
- 사용자가 답답해 보이면: 예상보다 오래 걸리고 있다는 점을 인정하고, 더 빠르게 진행할 방법을 제안하기
- 항상 사용자가 프로세스를 조정할 수 있는 자율성을 부여하기

**커밋/PR 정책:**
- Claude는 이 워크플로우 중 git commit, push, PR·MR 생성을 직접 수행하지 않습니다.
- 브랜치 전환, 커밋, PR·MR 생성이 필요한 시점에는 방법을 안내만 하고, 실행은 항상 사용자가 직접 하도록 요청하세요.

**맥락 관리:**
- 언급된 내용 중 빠진 맥락이 있으면 능동적으로 질문하기
- 공백이 쌓이도록 두지 말고, 발생하는 즉시 처리하기

**아티팩트 관리:**
- 전체 섹션 초안 작성에는 `create_file` 사용
- 모든 수정에는 `str_replace` 사용
- 수정할 때마다 아티팩트 링크 제공
- 브레인스토밍 목록에는 아티팩트를 쓰지 않기 - 그건 그냥 대화로 처리

**속도보다 품질:**
- 단계를 서두르지 않기
- 매 반복이 의미 있는 개선이 되도록 하기
- 목표는 실제로 독자에게 통하는 문서를 만드는 것

## 기술 문서 작업 시 참고 사항

- **다국어 번역이 예정된 문서**라면, 1단계 컨텍스트 수집에서 대상 언어와 번역 도구(Crowdin)를 미리 확인하면 2단계 표현 선택(직역하기 쉬운 문장 구조, 존칭/격식 수준 등)에 도움이 됩니다.
- **Docusaurus 기반 문서**처럼 MDX/frontmatter 구조가 있는 경우, 자리표시자 단계에서 frontmatter 필드(제목, sidebar_position, 태그 등)도 함께 스캐폴딩하면 좋습니다.
- **API 레퍼런스나 SDK 문서**의 경우, 브레인스토밍 단계에서 실제 스펙 파일(OpenAPI YAML, Doxygen 등)을 참고 자료로 함께 검토하도록 안내하세요.
- **문체 규칙**: 초안 작성/다듬기 단계마다 "~경우" 자제, "~때"/"~시" 사용, 명령형 문체 등 문서 작성 스타일 규칙을 함께 점검하세요.
- **결과물을 저장소 파일로 남길 때**: 임의 파일명 대신 프로젝트 규칙을 따르세요 — 한국어 원본은 `docs/`에 kebab-case 파일명으로 생성, frontmatter에 `title` 지정, 완료 후 `sidebars.js`에 항목 추가, `yarn start`로 미리보기 확인.
- **한국어 맞춤법 검사**: `mcp-korean-spell` MCP 서버를 완료 근접 시점/최종 검토 단계에서 활용해 맞춤법을 점검하세요.
